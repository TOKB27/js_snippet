# ADR-001: フロントエンド技術スタックの選定

## 1. コンテキスト（背景・システム前提・要求仕様）

### 1.1 システム概要と前提アーキテクチャ
本プロジェクトは、企業内の各種データ・リソースを一元集約・管理・運用するための「情報一元管理プラットフォーム」の構築を目的としています。
本システムは全体として以下のAWSサーバーレス＆マネージドサービスを基盤とする堅牢なフルスタックアーキテクチャを採用しています。

```
[クライアントブラウザ]
       │
       ▼
[Amazon CloudFront] ── (Viewer Request) ──> [Lambda@Edge (Cognito トークン検証 / 認可)]
       │
       ├─ (静的アセット取得) ─────────────> [Amazon S3 (SPA ホスティング)]
       │
       ▼ (API リクエスト: Bearer Token)
[Amazon API Gateway (Cognito オーソライザー)]
       │
       ▼
[AWS Lambda (Python 3.12+)] ── (認証情報取得) ──> [AWS Secrets Manager]
       │
       ▼ (VPC / プライベート接続)
[Amazon RDS for PostgreSQL] <── (SSH Bastion / 運用保守) ── [Amazon EC2 (踏み台)]
```

### 1.2 フロントエンドに求められる4大要求仕様
1. **エンタープライズ管理画面特有の複雑なUI要件**:
   - PostgreSQL に格納されたリレーショナルデータを一覧・編集・可視化するための高機能データグリッド（ソート、複合フィルタ、ページネーション、インライン編集、CSVエクスポート等）。
   - 厳格なバリデーション付き入力フォーム、ツリー構造表示、ダイアログ制御を短期間で高品質に構築できること。
2. **Lambda@Edge / S3 静的ホスティングとの完全な適合**:
   - Node.js サーバー等の常駐プロセスを不要とし、エッジ認可基盤とシームレスに結合する純粋な SPA（Single Page Application）構成であること。
3. **バックエンド（Python/PostgreSQL）との厳密な型整合性**:
   - DBスキーマや Pydantic モデルとフロントエンドの型定義を一致させ、ランタイムエラーをビルド時に検知できる型安全性。
4. **CI/CD の極限的な高速化とコード品質の自動統制**:
   - 静的解析・フォーマットのオーバーヘッドを極小化し、設定競合を排除して開発者体験（DX）を最大化すること。

## 2. 決定事項（Decision）

フロントエンド領域の中核技術スタックとして以下を採用します。

| レイヤー | 採用技術 | 主要な役割 |
| :--- | :--- | :--- |
| **言語 / 型システム** | **TypeScript (Strict Mode)** | フルスタック型安全性の担保、ランタイムエラーの根絶 |
| **コアフレームワーク** | **React (Vite による SPA 構成)** | S3+CloudFront+Lambda@Edge 構成との親和性、豊富なエコシステム |
| **UI コンポーネント** | **Material UI (MUI v5+) / MUI X** | 業務管理画面向けコンポーネント（DataGrid等）の網羅、一貫したデザイントークン |
| **Lint / Format** | **Biome** | Rust 製単一ツールによる超高速な静的解析・整形、設定競合の排除 |

---

## 3. 代替案との詳細比較・採却理由

### 3.1 UI コンポーネント: Material UI (MUI) の選定

#### 比較検討した代替案
- **Chakra UI**: 柔軟なスタイル定義が可能だが、標準の高度なデータテーブルや業務系部品が不足。
- **Tailwind CSS + shadcn/ui**: カスタマイズ性に優れるが、コンポーネントコード自体を自前で保守する必要があり、大規模業務画面では車輪の再発明コスト大。
- **Ant Design (AntD)**: 管理系部品は豊富だが、TypeScript 型定義の柔軟性やカスタムテーマの設計において MUI に劣る。

#### 比較評価マトリクス

| 評価項目 | **Material UI (MUI)** (採用) | **Chakra UI** (不採用) | **Tailwind CSS + shadcn/ui** (不採用) |
| :--- | :--- | :--- | :--- |
| **管理系部品の網羅性** | **極めて高い** (`MUI X Data Grid`, `Autocomplete`, `TreeView` 等) | 中（高度なグリッドやピッカーは外部依存） | 中（Radix ベースで軽量だが、複雑グリッドは自作/別選定が必要） |
| **デザインシステムの一貫性** | Material Design 準拠。`Theme Provider` で一括統制 | 自由度が高い反面、複数人開発でUIの揺れが発生しやすい | クラス指定が自由すぎて、デザインルールの統制コストが大きい |
| **エンタープライズ実績** | 世界中の業務・管理システムでデファクトスタンダード | コミュニティ・導入実績ともに MUI より小規模 | 急成長中だが、コンポーネントコードを抱え込むため長期保守負担あり |
| **TypeScript / アクセシビリティ** | 厳格な型推論と WAI-ARIA 準拠が標準 | 良好 | 良好 |

* **採却・選定の決定打**:
  本システムでは「大量リレーショナルデータのテーブル一覧・編集・検索」が中核機能となります。Chakra UI や Tailwind では高度なデータグリッドを自作・統合するコストが膨大になります。MUI（および公式の `MUI X Data Grid`）を採用することで、車輪の再発明を完全に防ぎ、開発工数を 30% 以上削減しつつエンタープライズ品質を担保します。

---

### 3.2 コアフレームワーク: React (SPA) の選定

#### 比較検討した代替案
- **Next.js (App Router / SSR)**: サーバーサイドレンダリングおよびフルスタック機能。
- **Vue.js 3 (Composition API / Vite)**: 軽量かつ学習コストの低いリアクティブフレームワーク。

#### 比較評価マトリクス

| 評価項目 | **React (SPA)** (採用) | **Next.js (SSR)** (不採用) | **Vue.js 3** (不採用) |
| :--- | :--- | :--- | :--- |
| **S3 + CloudFront ホスティング** | **完全適合**（静的アセット配置のみ、インフラコスト月額数円〜） | Lambda Web Adapter や常駐 Node.js サーバーが必要となり、運用・コストが複雑化 | 適合（静的ビルド可能） |
| **Lambda@Edge 認可との統合** | **完全適合**（エッジで Cognito トークン検証、SPA 側は API 通信時に JWT 付与） | SSR ミドルウェアと Lambda@Edge 認可の二重管理・競合リスクが発生 | 適合 |
| **TypeScript 型推論の完全性** | **TSX による完全ネイティブ推論**（コンパイラが構文木を直接解析） | TSX による完全ネイティブ推論 | SFC (`.vue`) の独自パースが必要で、複雑な Generics / 型パズルで制約 |
| **MUI とのエコシステム統合** | 公式ネイティブサポート | 一部 SSR 境界（`'use client'`）の考慮が必要 | ラッパーや別UI（Vuetify等）が必要で、機能差・型定義の差異大 |
| **SEO 要件** | **不要**（社内・特定ユーザー認証必須の管理システムのため） | 強みだが、本要件では不要なオーバーヘッド | 不要 |

* **採却・選定の決定打**:
  本システムは認証必須の管理システムであり、SEO や初期描画の SSR は一切不要です。Next.js の導入は Node.js 実行環境の維持やコールドスタート問題といった不要な複雑性を生みます。S3 + CloudFront + Lambda@Edge による低コスト・高可用性・強固なエッジセキュリティには、ピュアな React (Vite SPA) が最も堅牢かつシンプルに適合します。

---

### 3.3 リンター・フォーマッタ: Biome の選定

#### 比較検討した代替案
- **ESLint + Prettier**: 従来の業界標準ツールチェーン。

#### 比較評価マトリクス

| 評価項目 | **Biome** (採用) | **ESLint + Prettier** (不採用) |
| :--- | :--- | :--- |
| **実行速度** | **約10〜25倍高速**（Rust 製単一バイナリ、単一構文木共有） | 遅い（Node.js ランタイム、別プロセス多重解析） |
| **設定保守性・競合** | `biome.json` 1つで完結（フォーマットとリントの競合ゼロ） | `.eslintrc`, `.prettierrc`, プラグイン間のルール衝突解決コスト大 |
| **CI パイプライン負荷** | 数秒で完了（GitHub Actions 等の実行時間・コストを極小化） | キャッシュなしでは数十秒〜数分を消費 |
| **ルールの厳格性** | 推奨ルール（Recommended）が極めて合理的で型安全・クリーンコードに直結 | プラグイン選定や独自チューニングに多くの時間を奪われる |

* **採却・選定の決定打**:
  「Prettier と ESLint の競合解消」「パッケージアップデート時のプラグイン破損」「CI 実行時間の肥大化」を完全に撲滅し、開発者がビジネスロジックと UI 実装に集中できる環境を確立するため Biome を採用します。

## 4. 影響とトレードオフ（Consequences）

### 4.1 プラスの影響（メリット）
1. **フルスタックアーキテクチャの統一と高可用性**:
   - S3 + CloudFront + Lambda@Edge + Cognito + API Gateway + Python Lambda + RDS PostgreSQL との境界線が明確化され、サーバー運用コストとコールドスタートを最小化。
2. **型安全なデータ連携**:
   - TypeScript 型定義とバックエンドの Pydantic モデル / PostgreSQL スキーマを同期させることで、インターフェース不整合による障害をビルド時に排除。
3. **UI 開発スピードと品質の最大化**:
   - MUI の充実したコンポーネント群と Biome による高速なコード品質統制により、プロトタイプから本番実装までのリードタイムを大幅短縮。

### 4.2 リスクと対策（Mitigation）
1. **MUI のバンドルサイズ肥大化リスク**:
   - **対策**: パス指定インポート（Tree-shaking）の徹底、Vite による Code Splitting（`manualChunks`）を設定し、初期ロード時のチャンクサイズを最適化。
2. **API Gateway との二重認可連携**:
   - **対策**: Lambda@Edge による HTML 取得時のエッジ認可に加え、React SPA 内（Axios/Fetch インターセプター）で Cognito JWT（ID/Access Token）を `Authorization: Bearer <token>` ヘッダーに自動付与し、API Gateway の Cognito オーソライザーで厳格に検証する。
